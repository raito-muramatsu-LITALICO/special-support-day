# Discovery

## Product
特別支援の先生の1日や重要場面を擬似体験できる、顧客理解と支援学習のための選択式RPG/シミュレーション。

## User
- 社内トライアル中のPdM。特別支援の先生が日々どんな意思決定をしているのか、時間をどう使っているのか、どんな迷いを抱えているのかを追体験したい。
- 社内支援員/初学者。問題行動をABC分析で整理し、支援の考え方をケースで学びたい。

## Problem
顧客である先生のペインを、資料やインタビュー要約だけでは身体感覚として理解しづらい。特に、子どもの支援の難しさ、保護者コミュニケーションの難しさ、時間不足が見えにくい。

## Desired Outcome
- ペイン深掘りモードでは、各判断の直後に「先生は何を守り、何を後回しにしたか」を記録し、現場の意思決定負荷、感情的負荷、記録・連携の負荷を社内で話せるようになる。
- ABC分析・支援学習モードでは、行動だけでなく先行事象、後続事象、環境調整、観察ポイントを考えられるようになる。

## Constraints
- 社用PCで外部パッケージ取得が不安定。
- 依存ゼロのHTML/CSS/JSで動かす。
- 事例は架空。
- 子どもを問題として描かず、先生の置かれた制約と支援判断に焦点を当てる。

## MVP
- 複数ケース: 基本の一日、登校しぶり、保護者との認識ズレ、交流学級との連携、行動の背景理解、ケース会議、校外学習準備、通級指導、授業準備・教材選定。
- モード選択: ペイン深掘りモード / ABC分析・支援学習モード。
- 各シーンで複数の選択肢。
- 選択により安心、クラス安定、保護者信頼、先生余力、時間、記録が変化。
- ペイン深掘りモードでは、各判断直後にペイン発掘チェックポイントを表示し、最後にペイン集計、Discovery Map、判断ログを表示。
- ABC分析モードでは、A/B/C整理、支援案、追加観察ポイントを表示。

## Latest Change: リソース制約による選択肢ロック

### Discovery Gate

1. Job: PdMが、先生が理想的な支援を知らないのではなく、残り時間や余力の制約で選べなくなる状況を追体験したい。
2. Timing: 体験中の選択直前に効く。後半で重い支援が選べなくなることで、時間不足と余力不足を身体感覚として理解しやすくする。
3. UI方針: 新画面は追加せず、既存の選択肢カードに「今は選べません」と理由を表示する。全選択肢が塞がる場合は、場を止めないため最低限の対応を1つ残す。
4. Evidence扱い: 選べなかった対応は、架空シミュレーション上のリソース制約シグナルであり、顧客事実ではない。
5. 次の検証: 実際の先生/支援員レビューで、どの対応が本当に時間・余力を大きく使うのか、閾値が厳しすぎないかを確認する。

### Implementation Note

選択肢ごとの `effects.time` と `effects.energy` の消費量から、必要な残り時間・先生の余力を自動推定する。実際の消費は、時間を1.35倍、余力を1.25倍にして、画面表示、メーター更新、判断ログを同じ実効値に揃える。

選択肢カードでは、定性的な「時間を大きく使う」ではなく、`実行に必要な余白: 残り時間 X / 先生の余力 Y` と `実際の消費: 残り時間 X / 先生の余力 Y` を表示する。リソースが足りない選択肢はdisabledにし、最終振り返りとMarkdownの `Resource Constraints` に、選べなかった対応、必要余白、実際の消費量を残す。

## Previous Change: 通級・授業準備ケース追加

### Discovery Gate

1. Job: PdMが、通級担当の一日、在籍学級連携、時間割調整、教材準備・教材選定の意思決定負荷を追体験したい。
2. Timing: 体験中の想起と、体験後のDiscovery Map/Markdown整理に効く。
3. UI方針: 新UIは追加せず、既存ケースライブラリに独立ケースとして追加する。
4. Evidence扱い: 追加ケースは架空シミュレーションであり、顧客事実ではない。通級担当や経験者レビューに持ち込む仮説として扱う。
5. 次の検証: 通級担当経験者に、場面のリアリティ、抜けている業務、教材選定の表現、連携先の描写が妥当かを確認する。

### Implementation Note

通級は「普段の授業」「在籍学級との連携」「時間の使い方」の3ケース、授業準備は「個別課題選定」「教材の使い回しと個別最適」「授業後の次回設計」の3ケースとして追加した。どちらも診断名や実在事例ではなく、先生の制約、見立て、準備、共有、時間配分に焦点を置く。

Markdownコピーは、ローカル `file://` ではClipboard APIが制限されることがあるため、自動コピーの成否に関わらずコピー用textareaを表示して選択状態にする。GitHub PagesのようなHTTPSでは自動コピーできる場合があるが、常に手動コピーできる状態を残す。

## Previous Change: Discovery Map

### Discovery Gate

1. Job: PdMが体験直後の判断ログを、ペイン分類、ニーズ仮説、次の検証問いへ変換し、Product Discoveryに持ち込みたい。
2. Timing: 体験後の整理とCodexでの再利用に効く。判断直後のメモ入力は既存checkpointを維持する。
3. UI方針: 新しい入力欄は増やさず、既存の最終振り返りとMarkdown出力を拡張する。
4. Evidence扱い: Discovery Mapは架空シミュレーションと体験者の選択から得た仮説であり、顧客事実ではない。
5. 次の検証: 実際の先生/支援員レビューで、分類と仮説が現場感に合うか、重要な抜けがないかを確認する。

### Implementation Note

判断で選ばれたペインシグナルを、時間・優先順位、記録・共有、保護者コミュニケーション、校内連携・役割分担、支援設計・見立て、心理的負荷・説明責任に分類する。分類は確定診断ではなく、次のインタビューやレビューに持ち込むための整理軸として扱う。

## Change Protocol

このプロトタイプの体験設計を変える時は、安易にUIを追加せず、先に以下を確認する。

1. 誰のどのJobを前に進める変更か。
2. その変更は、体験中の想起、体験後の整理、Codexでの再利用のどこに効くか。
3. 既存UIの追加ではなく、置き換え・削減で解けないか。
4. その体験ログは、顧客事実、体験者の解釈、プロダクト仮説のどれとして扱うか。
5. 次に検証すべき問いは何か。

実装する場合も、READMEとこのDiscoveryメモを合わせて更新する。

## Pain Coverage
- 子どもの支援の難しさ。
- 保護者コミュニケーションの難しさ。
- 時間不足。
- 記録負荷。
- 校内連携と見立てのズレ。
- 合理的配慮の設計負荷。
- 安心と参加、自立と保護、即時性と正確性のトレードオフ。
